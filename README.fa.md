# 🐉 hydra

**یک سر در خانه، چند سر در آن‌سوی مرز.**

## چه مشکلی رو حل می‌کنه؟

یک تونل معمولی سرور-به-سرور فقط **یک مسیر** بهت می‌ده. اگه اون مسیر افت کنه — که روی
لینک‌های بین‌المللی شلوغ مدام افت می‌کنه — پینگت می‌پره و بازی رو می‌بازی. نه مسیر جایگزینی
داری، نه سازوکاری برای جبران پکت گم‌شده، و اگه تونل UDP خام باشه ترافیکت توسط تجهیزات
میانی شکل‌دهی یا دراپ می‌شه.

hydra هر سه رو حل می‌کنه:

1. **چند خروجی، نه یکی.** سرور ایران هم‌زمان به هر تعداد سرور خارج که بخوای تونل مستقل
   نگه می‌داره. ترافیک روی سالم‌ترینشون سوار می‌شه.
2. **تصحیح خطای رو به جلو (FEC).** پکت گم‌شده از روی داده‌ی افزونه **بازسازی** می‌شه،
   نه اینکه دوباره فرستاده بشه. همین ارسال مجدد است که ۲٪ لاست را به یک پرش ۲۰۰ میلی‌ثانیه‌ای
   تبدیل می‌کند؛ FEC کاملاً حذفش می‌کند.
3. **پنهان‌سازی + رمزنگاری دولایه.** ترافیک UDP در قالب یک جریان TCP جعلی در می‌آید، پس
   شکل‌دهنده‌هایی که UDP را محدود می‌کنند اصلاً UDP نمی‌بینند.

## دقیقاً چه کار می‌کند — پکت به پکت

مسیر کامل یک پکت بازی در مود پیش‌فرض `full`:

```
 کلاینت بازی
      │
      │  ① پکت UDP بازی، حدود ۶۰ بایت
      ▼
 ┌──────────────────────────────────────────────┐
 │  wg0   —  وایرگارد، شبکه 10.77.0.0/24        │
 │  ② رمزنگاری: ChaCha20-Poly1305، +۳۲ بایت     │
 └──────────────────────────────────────────────┘
      │
      ▼
 ╔══════════════════════════════════════════════════════════╗
 ║                  سرور ایران (hub)                        ║
 ║                                                          ║
 ║  ③ مسیریابی سیاستی: قانون                                ║
 ║     `ip rule from 10.77.0.0/24 → table hydra`            ║
 ║     که مسیر پیش‌فرضش به خروجی‌ای اشاره می‌کند که           ║
 ║     hydra-watch الان بهترین تشخیص داده                   ║
 ║                                                          ║
 ║  ④ wg-de1 — لایه‌ی دوم وایرگارد، یکی به‌ازای هر خروجی.     ║
 ║     Endpoint اش 127.0.0.1 است، پس پکت رمزشده به یک       ║
 ║     پروسه‌ی محلی تحویل داده می‌شود نه مستقیم به کارت شبکه. ║
 ║                                                          ║
 ║  ⑤ UDPspeeder — لایه‌ی FEC. هر ۱۰ پکت را جمع می‌کند،      ║
 ║     ۵ پکت پاریتی Reed-Solomon می‌سازد، ۱۵ تا می‌فرستد.     ║
 ║     پرچم `--timeout 0` یعنی هرگز برای پر شدن دسته        ║
 ║     *منتظر نمی‌ماند*، پس صفر تأخیر اضافه می‌کند.           ║
 ║                                                          ║
 ║  ⑥ udp2raw — هر دیتاگرام را در یک هدر TCP مصنوعی          ║
 ║     می‌پیچد (faketcp)، یک دست‌دهی سه‌مرحله‌ای واقعی انجام   ║
 ║     می‌دهد تا فایروال‌های حالت‌مند یک جریان TCP معتبر       ║
 ║     ببینند، سپس با AES-128-CBC + HMAC-SHA1 رمز می‌کند.    ║
 ╚══════════════════════════════════════════════════════════╝
      │
      │  ⑦ از لینک بین‌المللی عبور می‌کند، در ظاهر TCP
      ▼
 ╔══════════════════════════════════════════════════════════╗
 ║                  سرور خارج (exit)                        ║
 ║  ⑧ udp2raw پوسته‌ی faketcp را برمی‌دارد و رمزگشایی می‌کند  ║
 ║  ⑨ UDPspeeder پکت‌های گم‌شده در مرحله ⑦ را بازسازی می‌کند  ║
 ║  ⑩ wg-de1 رمزگشایی و NAT به اینترفیس عمومی                ║
 ╚══════════════════════════════════════════════════════════╝
      │
      ▼
 سرور بازی
```

مسیر برگشت دقیقاً آینه‌ی همین است.

### حلقه‌ی فیل‌اوور، که موازی اجرا می‌شود

هر ۵ ثانیه `hydra-watch` به IP داخلی **همه‌ی** خروجی‌ها از طریق اینترفیس اختصاصی خودشان
پینگ می‌زند و محاسبه می‌کند:

```
امتیاز = میانگین پینگ  +  ۲ × جیتر  +  ۲۰ × درصد لاست      (کمتر = بهتر)
```

جیتر و لاست وزن بسیار سنگین‌تری از پینگ خام دارند، چون یک لینک پایدار ۹۰ میلی‌ثانیه‌ای
بهتر از یک لینک ۶۰ میلی‌ثانیه‌ایِ لرزان است. خروجی جدید فقط وقتی برنده می‌شود که
**۱۵٪ بهتر** باشد و **۳ بار پشت‌سرهم** بهتر بماند — همین هیسترزیس جلوی جابه‌جایی
مداوم و بی‌فایده‌ی مسیر را می‌گیرد.

وقتی سوییچ می‌کند، فقط یک خط را بازنویسی می‌کند: مسیر پیش‌فرض داخل جدول مسیریابی `hydra`.
بقیه‌ی تونل‌ها گرم و برقرار می‌مانند، پس فیل‌اوور یک تغییر مسیرِ زیر یک ثانیه است، نه اتصال مجدد.

### هر لایه واقعاً برای چیست

| لایه | وظیفه | بدونش چه می‌شود |
|---|---|---|
| WireGuard | محرمانگی، جامعیت، سرعت درون‌کرنلی | ترافیک قابل خواندن؛ رمزنگاری کند فضای کاربر |
| UDPspeeder | تصحیح خطای Reed-Solomon | هر پکت گم‌شده تبدیل به توقف یا پرش ارسال مجدد می‌شود |
| udp2raw | پنهان‌سازی faketcp + لایه‌ی دوم رمز | شکل‌دهنده‌های UDP تونل را خفه یا دراپ می‌کنند |
| مسیریابی سیاستی | هدایت شبکه‌ی کاربران به خروجی منتخب | فقط یک خروجی قابل استفاده است |
| hydra-watch | امتیازدهی سلامت و فیل‌اوور | خروجی خراب همچنان انتخاب می‌ماند |
| BBR + sysctl | کنترل ازدحام، اندازه‌ی بافرها | بافربلوت؛ لاست به‌اشتباه ازدحام خوانده می‌شود |

### یک نکته‌ی صادقانه درباره‌ی BBR

BBR یک الگوریتم کنترل ازدحام برای **TCP** است. ترافیک بازی تو UDP است و داخل WireGuard
سوار می‌شود، پس BBR مستقیماً کنترلش نمی‌کند. چیزی که BBR واقعاً اینجا بهت می‌دهد:

- جریان‌های TCP *داخل* تونل (دانلود، وب، سیگنالینگ ویس‌چت) دیگر بافرها را پر نمی‌کنند و
  تأخیر بقیه را بالا نمی‌برند.
- فریم‌های `faketcp` سوکت خام‌اند، پس BBR روی آن‌ها هم اعمال نمی‌شود — اما صف‌بندی `fq`
  که همراهش فعال می‌شود کل ترافیک خروجی را زمان‌بندی می‌کند و این به‌طور قابل‌اندازه‌گیری
  جیتر را کم می‌کند.

خلاصه: فعال کردن BBR ارزشش را دارد، و مجموعه‌ی sysctl دور و برش (اندازه‌ی بافرها،
`rp_filter=2` برای مسیریابی نامتقارن چند-خروجی، `tcp_slow_start_after_idle=0`) برای این
بار کاری از خودِ BBR مهم‌تر است. هر کسی BBR را به‌عنوان درمان جادویی پینگ بهت می‌فروشد،
دارد بزرگش می‌کند.

## مقایسه با تونل تک-لینک

| | تونل تک-لینک معمول | hydra |
|---|---|---|
| سرور خارج | ۱ | تا ۲۵۰، هم‌زمان |
| جبران پکت گم‌شده | ندارد | Reed-Solomon FEC |
| فیل‌اوور خودکار | ندارد | امتیاز پینگ+جیتر+لاست، هر ۵ ثانیه |
| رمزنگاری | معمولاً یک لایه | ChaCha20-Poly1305 + AES-128-CBC/HMAC-SHA1 |
| فرار از شکل‌دهی UDP | متغیر | faketcp با دست‌دهی واقعی |
| تیونینگ کرنل | ندارد | BBR، fq، بافرها، rp_filter |
| اجرا | اغلب داکر | باینری ساده + systemd |

## نصب

یک خط، روی **هر دو** طرف — هم سرور ایران، هم هر سرور خارج:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/devprogrmer/hydra/main/install.sh)
```

پیش‌نیازها را نصب می‌کند، باینری‌ها را می‌گیرد، تیونینگ کرنل را اعمال می‌کند و یک منوی
تعاملی باز می‌کند. اولین سؤالش این است که این سرور چیست:

```
   1) سرور ایران (هاب)  — کاربرها بهش وصل می‌شن، به چند سرور خارج تونل می‌زنه
   2) سرور خارج         — خروجی؛ با توکنی که هاب می‌ده وصل می‌شه
```

### بعدش، روی سرور ایران

منو ← **ساخت تونل جدید** ← یک نام و آی‌پی سرور خارج بده ← مود را انتخاب کن.
یک خط آماده‌ی پیست چاپ می‌شود. همان خط را روی سرور خارج اجرا کن تا لینک بالا بیاید:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/devprogrmer/hydra/main/install.sh) apply <TOKEN>
```

برای هر سرور خارج تکرارش کن. بعد منو ← **مدیریت کاربران** ← **کاربر جدید** تا کانفیگ
وایرگارد همراه کد QR بگیری.

از این به بعد هر وقت `hydra` بزنی همان منو باز می‌شود.

### منو

```
   1) ساخت تونل جدید        اضافه کردن یک سرور خارج
   2) مدیریت تونل‌ها         حذف، پین، ری‌استارت، توکن
   3) مدیریت کاربران         کانفیگ وایرگارد + QR
   4) تنظیم FEC             فعلی: 10:5
   5) فوروارد پورت بازی
   6) اعمال دوباره‌ی BBR و تیونینگ
   7) رویدادها و لاگ
   8) حذف کامل
   0) خروج
```

صفحه‌ی اصلی یک جدول زنده از همه‌ی خروجی‌ها نشان می‌دهد: پینگ، جیتر، لاست، و اینکه
همین الان کدام‌یک ترافیک را حمل می‌کند.

## استفاده‌ی روزمره

کافی است `hydra` بزنی تا منو باز شود. همه‌چیز همان‌جاست — وضعیت، پین کردن خروجی،
افزودن کاربر، فوروارد پورت، FEC، لاگ.

چند مورد برای اسکریپت و مانیتورینگ بدون منو هم در دسترس است:

```bash
hydra status                      # جدول زنده‌ی خروجی‌ها
tail -f /var/log/hydra.log        # تاریخچه‌ی سوییچ‌ها
journalctl -u hydra-raw@de1 -f    # لاگ یک تونل مشخص
```

## تنظیم FEC — مهم‌ترین پارامتر

منو ← **تنظیم FEC**. خودش پروسه‌های FEC را ری‌استارت می‌کند. فرمت `داده:پاریتی`:

| لاست اندازه‌گیری‌شده | مقدار | سربار پهنای باند |
|---|---|---|
| زیر ۱٪ | `20:5` | ۲۵٪ |
| ۱ تا ۵٪ | `10:5` (پیش‌فرض) | ۵۰٪ |
| ۵ تا ۱۵٪ | `8:8` | ۱۰۰٪ |
| بالای ۱۵٪ | `4:8` | ۲۰۰٪ |

**روی هر دو سر یک مقدار** بگذار — اگر یکی نباشند لینک بالا نمی‌آید. ترافیک بازی حجمش
ناچیز است، پس این سربار معمولاً اهمیتی ندارد مگر دانلود سنگین هم از تونل رد کنی.

### فوروارد پورت بازی

منو ← **فوروارد پورت**. هرچند پورت که خواستی، جداشده با کاما، بازه با خط‌تیره:

```
50820,51820,2097,2096,443,80
27015,7777-7784
```

هر چیزی که به این پورت‌ها روی آی‌پی عمومی سرور ایران بخورد، با DNAT به خروجی انتخابی
فرستاده می‌شود. TCP، UDP، یا هر دو.

پورت‌ها در رول‌های `multiport` جمع می‌شوند — شش پورت بالا **یک** رول iptables به‌ازای هر
پروتکل می‌شوند، نه شش تا. لیست‌های بلندتر از سقف ۱۵‌تایی multiport خودکار تکه می‌شوند
(هر بازه دو ورودی حساب می‌شود).

رول‌ها در چین‌های اختصاصی `HYDRA_PRE` / `HYDRA_POST` / `HYDRA_FWD` می‌نشینند، پس تمیز
بازسازی می‌شوند و هیچ‌وقت رول تکراری روی هم تلنبار نمی‌شود. بعد از ریبوت و بعد از هر
ری‌استارت تونل دوباره اعمال می‌شوند.

**یک هشدار که نباید ازش رد شوی:** لیستت با پورت‌هایی که این سرور برای در دسترس ماندن لازم
دارد مقایسه می‌شود — SSH، پورت وایرگارد کاربران (پیش‌فرض ۵۱۸۲۰)، و پورت udp2raw هر تونل.
فوروارد کردن `51820` یعنی ترافیک وایرگارد خود کاربرانت به خروجی می‌رود و همه قطع می‌شوند؛
فوروارد کردن پورت SSH یعنی خودت از سرور بیرون می‌مانی. یک تأیید صریح با نام پورت‌های
متعارض می‌گیری و پاسخ پیش‌فرض «نه» است.

## مودها

| مود | زنجیره | چه وقت |
|---|---|---|
| `full` | WG → FEC → faketcp | پیش‌فرض. وقتی UDP شکل‌دهی یا مسدود می‌شود. |
| `fec` | WG → FEC | وقتی faketcp روی آن VPS کار نمی‌کند (محدودیت سوکت خام). |
| `plain` | فقط WG | مسیر تمیز است و فقط چند-خروجی و فیل‌اوور می‌خواهی. |

## عیب‌یابی

| علامت | بررسی |
|---|---|
| handshake نمی‌گیرد | `journalctl -u hydra-raw@NAME -n 50` — معمولاً پورت TCP در فایروال سرور خارج بسته است |
| udp2raw وصل نمی‌شود | پرچم `--lower-level auto` را به سرویس اضافه کن (برخی VPSها با iptables تداخل دارند) |
| پینگ خوب است ولی ترافیک رد نمی‌شود | `ip rule show` و `ip route show table hydra` |
| سایت‌ها باز نمی‌شوند | `WG_MTU` را در `/etc/hydra/exits.d/NAME.conf` پله‌پله کم کن: ۱۲۸۰ → ۱۲۴۰ → ۱۲۰۰ |
| BBR فعال نشد | کرنل قدیمی است؛ `uname -r` باید ≥ ۴.۹ باشد |

## نکات امنیتی

- کلید خصوصی وایرگاردِ سرور خارج روی هاب تولید می‌شود و داخل توکن سفر می‌کند. توکن‌ها را
  از کانال امن منتقل کن و بعد `shred -u /etc/hydra/token-*.txt`.
- `hydra-exit apply` فقط خطوط `KEY=VALUE` را می‌پذیرد و توکن دستکاری‌شده را رد می‌کند.
- تمام فایل‌های کانفیگ با `chmod 600` نوشته می‌شوند.
- **قبل از اجرا روی سرور واقعی، اسکریپت‌ها را خودت بخوان.** این کد در شرایط شبکه‌ی زنده
  تست نشده است.
